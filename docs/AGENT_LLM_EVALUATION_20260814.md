# 本地语言模型 Agent 工具链冒烟评测（2026-08-14）

> 口径修正：本报告只覆盖代码修复、仓库维护和证据报告三个技术型沙盒任务，用于验证 Hermes 工具调用、文件修改和外部 grader。它不代表自媒体写作、运营分析、行业/竞品/产品调研、业务方案、PPT 或访谈分析能力。正式业务场景计划见 `docs/AGENT_BUSINESS_EVALUATION_PLAN_20260814.md`。

## 结论

本轮是正式业务评测前的工具链冒烟：通过 Hermes Agent 让模型真实读取文件、调用终端、修改沙盒、运行验证并形成最终答复。

`Qwen3.6-27B-Fable` 首次三任务通过 2/3（66.7%），未达到 80 分生产门槛所对应的稳定可用要求。它能完成边界明确且有确定性测试闭环的代码修复与仓库维护，但证据型报告首次在 600 秒停止线超时，且超时前生成的 Markdown 内部出现 P95 28.09 / 29.76 两套数值。修正题目判分歧义后重试能够形成正确、一致、证据可核验的结果，但仍耗时 555.06 秒。

因此只能初步判断 27B 在技术型工具任务中的行为，不能据此决定业务场景默认模型。精确统计仍应交给确定性脚本，模型只负责取证编排、解释和建议。

`Qwen3-30B-A3B` 只获得 1 个有效质量样本：它在 39.76 秒内结束，但误称找不到 `order.py`，没有修改真实目标文件，测试失败。随后两题因当前 llama-server 只向 Hermes 报告 16,384 上下文、低于 Hermes Agent 的 65,536 最低要求而未启动。这两题记为基础设施未测，不记成模型质量失败。

## 评测环境

- 机器：Apple M5，32 GB 统一内存
- Agent 框架：Hermes Agent v0.20.0（2026.8.3）
- 推理后端：llama.cpp 9830，OpenAI-compatible API
- 工具集：`terminal,file`
- 网络：任务明确禁止访问
- 隔离：每题独立工作目录
- 单题停止线：600 秒
- 判定：外部自动 grader 优先于 Agent 最终陈述

## 有效能力证据

### 27B：适合有硬验证的确定性任务

代码修复题只修改 `src/order_summary.py`，未修改测试；2 个单元测试全部通过。仓库维护题只修改 README 与 JSON 注册表，保留 RealVisXL 的 profiles/notes、其他工具和未知字段，隐藏检查通过。

这说明它在以下条件下可用：任务边界明确、文件量小、预期变更可描述、存在测试或 schema 校验、允许 4–5 分钟延迟。

### 27B：证据报告需要“脚本算、模型写”

首次报告虽然正确算出了 29.76 秒，却在摘要表写成 28.09 秒，并未在 600 秒内正常结束。修正版重试的 JSON 与 Markdown 一致，说明模型有能力完成，但时延与首次稳定性不足。

默认方法应拆为：解析/统计脚本生成唯一 JSON 真值 → Agent 引用 JSON 撰写 Markdown → 外部 checker 对数字和结论做一致性校验。禁止让模型同时承担日志解析、统计计算、双格式复制与自我验收。

### 30B：当前还不是可比较状态

第一题的失败显示其工具/文件定位至少有一次明显失误；但后两题没有进入模型执行，不能据此宣布 30B 总体 0/3。需先建立独立 64K Agent 配置，再按完全相同的三题重跑。

## 评测器修正记录

首轮还发现两条 rubric 缺陷，并已修复：

1. `29.76 <= 30.0` 的延迟布尔断言最初写反；
2. 题目未限定 `failed_cases` 的元素结构，grader 却只接受字符串数组。现在同时接受 `['B']` 和包含 `case_id: B` 的对象数组。

原始结果没有覆盖；修正规则后的复核单独写入 `results/agent/20260814-fable27b-evidence-retry/regrade.json`。首次任务仍因超时和 Markdown 内部数值矛盾保持失败。

## 当前最佳使用方法

1. 本地 27B 仅用于低频后台 Agent：小范围代码修复、配置同步、批量维护；必须给出工作目录、禁止项、验证命令和停止线。
2. 任何数值报告采用确定性脚本生成 JSON，模型不得成为唯一计算器。
3. Agent 最终回答不作为通过证据；以测试、schema、文件哈希和外部 grader 为准。
4. 默认每题 600 秒止损；交互式小任务若 180 秒仍未形成有效变更，应切换更快模型或在线 Agent。
5. 30B/35B 横评前先使用独立服务配置至少 64K 上下文，避免修改当前 16K 内容生成档并混淆性能结论。

## 下一步

1. 为 30B、35B 建立独立的 Hermes Agent 64K 测试配置，重跑同一三题；分别记录模型质量失败和基础设施失败。
2. 扩展到 8 个场景：长交接执行、歧义澄清、失败恢复、安全边界、多步流水线编排。
3. 每个候选至少重复两次，报告首次通过率、重试通过率、无效修改率、延迟、API 调用和 token。
4. 完成后再决定本地质量档、快速档与在线 Agent 的任务路由。

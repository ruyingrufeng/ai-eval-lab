# 性能、资源与并行评测规范

记录时间：2026-08-12 11:42:17 +08:00。

质量通过不代表生产可用。所有工具与模型必须同时回答四个问题：单任务多快、占用多少系统资源、多任务时吞吐如何、与其他生产组件共存时是否稳定。

## 三种执行形态

### 1. 单任务基线

一次只运行一个请求，用于得到冷启动、热运行、服务加载、推理和保存阶段的基准。至少记录：

- 端到端延迟、模型推理时间、首结果延迟；
- CPU 使用率、系统物理内存、内存压力、压缩内存、swap 用量；
- 进程 RSS 仅作辅助，不把它当作 Apple 统一内存总占用；
- 磁盘读写、输出大小、失败或警告；
- 无风扇机器的运行序号、持续运行时间和降速比例。

### 2. 队列并发

向同一个服务同时提交多个请求，测量服务是否排队、拒绝、崩溃或失去响应。ComfyUI 常见行为是并发接收、GPU 串行执行，因此必须记录：

- 提交并发数、队列深度、每个请求的排队时间与执行时间；
- 总 wall time、吞吐量、p50/p95 延迟、公平性；
- 请求错误率、超时率、队列恢复和取消行为；
- 结果顺序与固定 seed 复现性。

不能把“同时提交成功”写成“GPU 并行生成成功”。

### 3. 真正共存负载

让不同服务或进程同时占用 CPU/GPU/统一内存，例如：

- 图像 + 本地 LLM 推理；
- 图像 + TTS；
- 图像 + FFmpeg/HyperFrames/Remotion 渲染；
- LLM + TTS + 媒体编码。

该测试评估本地内容工厂的实际调度能力。记录每个任务相对单任务基线的延迟增幅、吞吐下降、内存压力、swap 增量、错误和恢复时间。

## 系统级采样字段

每次采样应包含：

- 时间戳与相对测试开始秒数；
- `top` 的 CPU user/system/idle 与 PhysMem；
- `memory_pressure -Q` 的可用比例；
- `vm_stat` 的 free/active/inactive/wired/compressor/pageout；
- `sysctl vm.swapusage`；
- 目标 PID 的 RSS、CPU、运行时间；
- `pmset -g therm` 可获得的 thermal/performance warning；
- 服务 API 健康状态与队列深度。

macOS 没有稳定公开的 GPU 显存/功耗/温度接口时，必须明确写 `not_available`，不得用 RSS 猜测。

## 并行矩阵

| 等级 | 场景 | 并发 | 用途 |
|---|---|---:|---|
| C0 | 单请求 | 1 | 冷/热基线 |
| C1 | 同服务队列 | 2 | 交互与后台任务同时提交 |
| C2 | 同服务队列 | 4 | 队列上限、延迟与恢复 |
| X1 | 图片 + LLM | 1+1 | 写稿同时生成配图 |
| X2 | 图片 + TTS | 1+1 | 旁白和配图并行 |
| X3 | 图片 + 视频渲染 | 1+1 | 成片阶段资源争用 |
| X4 | LLM + TTS + FFmpeg | 1+1+1 | 非扩散型内容流水线 |

先测 C0/C1，再逐级提高；若出现红色内存压力、swap 快速增长、系统无响应或重复崩溃，停止更高并发。

## 关键指标

- **吞吐**：单位时间完成的图片、token、音频秒或视频帧；
- **延迟**：平均值之外必须报告 p50/p95 和最慢值；
- **并行效率**：`单任务耗时 × 任务数 ÷ 并行总 wall time`，队列串行约接近 1，不代表 GPU 真并行；
- **干扰系数**：共存时任务耗时 ÷ 单任务耗时；
- **资源增量**：测试前后物理内存、压缩内存和 swap 差值；
- **降速率**：后续运行相对首个稳定运行的耗时增幅；
- **稳定性**：成功率、OOM、Metal 错误、服务假活、超时和人工重启次数。

## 通过条件

每个候选必须声明目标服务等级，而不是使用统一并发数字：

- 交互工具：C1 下服务仍可响应，p95 延迟有上限；
- 后台批处理：允许排队，但必须 100% 完成并可恢复；
- 生产组合：至少通过一个与其真实用途相符的 X 场景；
- 32 GB 主机上不得依赖持续高 swap 才能完成常规任务；
- 任一任务出现系统级严重内存压力、不可恢复假活或需要强杀，不进入推荐并发配置。

具体阈值在得到首轮数据后按内容类型确定。测试默认串行升级并发，避免未经测量直接压满机器。

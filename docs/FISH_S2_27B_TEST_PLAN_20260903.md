## 1. 目标、范围与完成定义

回答三件事：

1. 一章合成小说分段配音能否完整生成，是否漏句、重复、截断或拼接异常？
2. 固定参考音频后，同一个角色跨段落、跨情绪是否仍像同一个人？
3. 卸载其他大模型后，Fish 的速度、统一内存和持续运行稳定性如何？

本轮服务目标是**本机单任务、串行、人工复核的离线配音**，不是实时交互服务或整本书无人审核生产。只使用中性、虚构的成年角色及既有合成参考音频，不采集真人声音。

本方案要求交付可复核证据，不要求结果必须通过。运行失败、资源超限、用户未听评都应如实记录。**27B 不能通过总结“效果不错”替代实测或人工验收。** 当前登记仍为 `runnable`；不要自行更新推荐栈。

## 3. 工作分三次交接：准备 → 独立运行 → 分析

### 阶段 P：27B 只准备，不卸载自己

1. 核验上述文件和环境；记录 Git 原有未提交修改，不清理、不覆盖。
2. 在项目 `scripts/` 新建本轮专用执行器、资源监控与分析脚本。复用现有库和参考音频，保持原版 `tts.py` 与旧报告可用。
3. 实现以下明确接口（**这些脚本尚不存在，是本轮执行者需要实现的内容**）：

```text

scripts/fish-s2-followup.py check --run-id <id>
scripts/start-fish-s2-followup.sh <id>
scripts/fish-s2-followup.py status --run-id <id>
scripts/fish-s2-followup.py analyze --run-id <id>
```

4. `prepare` 生成固定测试清单、文本、顺序、随机种子、参数和 SHA-256；`check` 只做校验和干运行，**不加载 Fish/ASR**。主任务 ID、预期数量、恢复策略和输出路径必须在卸载 27B 前落盘。

6. 向用户交付**实际已创建并通过 check 的一条启动命令**，明确提示进入独立运行前暂停本地 Agent 请求并卸载 27B。此时结束当前 Agent 回复，不在自己的执行工具调用里同步等待自己被卸载。

### 阶段 R：用户或外部控制器启动，测试期间不调用 27B

推荐用户暂停本地模型任务，使用现有管理方式卸载已加载权重，再在独立终端执行启动命令。保留 llama-server 管理进程是允许的，关键是权重不驻留、没有推理请求。

## 5. 固定测试矩阵

| 编号 | 测试 | 规模与执行方式 | 要回答的问题 |
|---|---|---|---|
| T0 | 旧样例独立复测 | 对第一轮 13 条相同输入、种子和参数重跑；沿用原参考，保存到新目录，不重新抽取角色声线 | 当前空闲条件是否改善？注明参考是否与第一轮生成结果逐字节一致，差异不混算 |
| T1 | 一章分段生成 | 1,200–1,600 个中文字符的合成章节，旁白/A/B；默认每段 40–60 字，最多 80 字且按完整句子边界分割，最多 40 段；seed 42 | 段落完整性、对话归属、长任务稳定性、拼接 |
| T2 | 边界与重复性 | 从章节冻结 6 个较难片段：数字日期、多音字、停顿、连续对白、情绪转换等；每条追加 seeds 123、321，共 12 段 | 是否只有某一次碰巧正常？ |
| T3 | 同声线不同情绪 | 3 个角色 × 普通/兴奋/悲伤 × seeds 42、123，共 18 段；每个角色三种版本使用同一测试句、同一参考音频 | 情绪有没有效果，变化时会不会换人？ |
| T4 | 跨阶段角色锚点 | 3 角色 × 开头/中间/结尾，共 9 段；每个角色固定中性测试句和同一 seed | 模型复用前后声线一致性；不把独立段落测试误称模型记住全文 |
| T5 | 持续负载 | 同一 Fish 进程串行执行以上任务，累计活跃生成不足 30 分钟时，用固定中性短句补测；总上限 120 个生成任务 | 无风扇机器持续运行是否降速或出错？ |

T4 锚点插入完整任务队列的前部、中部、尾部。若 T5 增加任务，要把结尾锚点安排在补测后。不能先跑完“结尾”再继续工作却宣称它代表整轮结束。

默认 `max_new_tokens=512`，MLX 上限 12GiB、allocator cache 256MiB，使用现有采样默认参数；T0 严格复用历史每条参数。不得传入会被上游忽略的 temperature/top-p 伪装成调参。参考音频每个角色编码一次并复用，编码耗时单列。

达到 token 上限或文本异常时，保留失败样本及原因；主基准不隐式重试、不换种子、不自动扩大上限。允许本轮结束后另建 `repair_attempts`，只对最多 3 个失败片段各做一次有明确变更的恢复尝试。恢复成功不覆盖原失败率，也不能改写第一轮通过率。

T5 若遇到 120 任务上限或总运行时限而不足 30 分钟，应写 `insufficient_duration`，不靠空等补足稳定性时间。

## 6. 资源、速度与长期运行采样

资源监控独立于模型 worker，每 2 秒记录时间戳、memory pressure、swap、vm_stat（含页大小、wired/compressor/pageout）、进程 RSS/CPU。thermal 状态每 30 秒取一次。缺失字段写 `not_available`，不能造默认零值；判定需要的字段连续 3 次缺失则停止，以免失去保护。

逐任务记录：`case_id, phase, role_id, seed, input_hash, reference_hash, config_hash, queued_at, started_at, ended_at, output_path, output_sha256, exit_status, generated_tokens, hit_token_limit, sample_rate, audio_seconds, generation_seconds, rtf, mlx_peak_gib, warnings`。每段结束 fsync/可靠落盘；输出先写临时文件，完成检查后原子改名。

报告至少包括：

- 加载时间（说明系统文件缓存可能命中，别伪称硬冷启动）、参考编码时间、首段、热段、整体墙钟时间。
- 加权 RTF = 总生成秒 / 总音频秒；每段 RTF 的 p50/p95（写明 quantile 方法、样本数）与最慢项。
- 任务通过率、异常、OOM/Metal 错误、超时、恢复尝试；逐段与总输出校验。
- memory pressure、swap 起止/采样峰值/增量、压缩内存、pageout 增量；RSS 和 MLX 值分别列示，不相加。
- 前、中、后同一句锚点的 RTF 对照；用每组中位数比较末段/前段，不能用不同文本的生成秒数归因于降频。
- 第一轮与 T0 的输入/参考/参数匹配表：完全可比的项才计算历史与本次的 RTF 比值；没有受控同步 A/B 时，只称历史对照，不能称已证明后台负载导致多少倍减速。
- 本轮无 streaming 接口：首包延迟写 `not_applicable`，不是 0。

## 7. 内容完整性与 ASR

Fish 全部退出后，使用现有本地 Qwen3-ASR 模型逐段转写，不把整章一次塞入 `max_new_tokens=256` 的 ASR 调用。每条转写关联原 case ID、文件哈希和期望文本，保存原文与原始转写到排除目录。

1. 参考规范化只做 NFKC、去标点/空白、去输入中的合法情绪/说话人标签；保留原始数据，不将“她/他”等同音字自动改成正确答案。
2. 计算字符编辑距离、逐段 CER、加权总体 CER（编辑距离总和/参考字符总数）、文本长度比、末尾 10 个字的覆盖与重复疑点。尾部短、样本少时注明敏感性。
3. 对连续重复、尾句缺失、读出标签、数字/日期偏差、多音字疑点生成 `review_flags.json`；检测规则和触发证据必须保留。ASR 的疑点不直接等同 TTS 错误。
4. 拼接验收：清单 ID 顺序完全一致、无缺段/重段，采样率一致；拼接时长与逐段时长之和 + 固定间隔误差 ≤ 0.1 秒；保存时间轴，所有音频能解码。
5. 角色正确性有两层：脚本绑定的 reference hash 必须正确；实际听起来是否为该角色需人工试听，不能只看 JSON 的 role 字段通过。

## 8. 本轮预先冻结的判定标准

下面是**本轮拟定的操作门槛，不是此前实测结论或行业标准**。执行者不能为了让结果通过而修改。

| 维度 | 本轮标准 |
|---|---|
| 执行完整 | 主任务计划完成 100%；无崩溃/OOM/Metal 错误；无 token 上限截断；无静音空文件或非有限数据；不以重试覆盖首次失败 |
| 输出格式 | 44.1kHz 单声道；可解码；波形超幅比例 ≤ 0.01%，超过则列为异常，不预先限幅来掩盖 |
| ASR 自动筛查 | 全体加权 CER ≤ 8%；每段 CER > 15%、长度比不在 0.85–1.15、尾部疑似缺失或重复均强制人工复核；通过自动筛查仍不能替代听评 |
| 内容最终裁决 | 所有疑点都有人工处理结果；不允许确认的漏句、重复句、未读尾句或错配角色；只有同音字转写偏差可以经人工记录后豁免，原 CER 保留 |
| 非实时批处理速度 | 独立条件下加权 RTF ≤ 3.0、逐段 RTF p95 ≤ 5.0；更慢则速度门槛未通过，但可以单独记录用户是否愿意接受，不自动降阈值 |
| 持续稳定性 | 活跃生成 ≥ 30 分钟；末组锚点 RTF 中位数相对首组增幅 ≤ 30%；相同材料比较，样本不足写未验证 |
| 常规资源 | 无严重内存压力；独立基线起算 swap 峰值增量 ≤ 1GiB；更高说明常规工作仍依赖 swap，资源门槛未通过 |
| 角色与自然度 | 使用下面匿名试听表，由用户逐项填写；未填写就是 `pending_human_review` |

CER 高但人工确认只是 ASR 错误时，分别报告“自动筛查未通过、人工复核内容通过”，不能把自动项改为通过。任何核心项失败，保留 `runnable` 并说明可接受的使用边界。

## 10. 超时、止损与恢复

- 独立生成+回检总墙钟上限 **120 分钟**；Fish 生成阶段上限 **90 分钟**。时间从外部 worker 启动计算，不计前期编写脚本或用户听评时间。
- 单条生成超过 **180 秒**、ASR 单条超过 **120 秒**、心跳超过 **30 秒**不更新：结束该测试 worker，写超时记录，不继续后续负载。
- 第一次 OOM、Metal 错误、系统严重内存压力、模型外部进程意外加载，立即停止当前测试。
- memory_pressure 报告 critical/red，或其系统空闲比例连续 3 次低于 10%；相对独立基线 swap 增加超过 2GiB；60 秒内 swap 增加超过 1GiB：监控器停止测试。数值 10% 是本轮止损线，不把它解释为 macOS 官方颜色映射。
- 日志/输出磁盘剩余低于 **20GiB**，停止新增任务。只保存本轮产物，不清理用户文件以腾空间。
- 终止仅针对本轮记录的进程组：先 TERM，等 15 秒后仍不退出才 KILL；记录需要强杀即资源/恢复门禁失败。不得使用全局 `killall`/`pkill python`。
- 恢复仅在环境重新通过 preflight 后显式进行；核对 case/config/reference/output hash，已完成且有效的任务跳过，未完成任务在新 attempt 下执行，原失败仍计入主结果。
- 状态建议：`prepared / waiting_for_unload / running / aborted / failed / awaiting_human_review / completed`。`completed` 只表示任务与记录完成，不代表测试通过；另设 `verdict: pass/fail/pending`。

## 11. 并发与 verified 的边界

本轮不新建网络 API，也不同时加载多个 Fish worker。C1/C2 如果没有真正可复用的队列接口，明确记 `not_tested`；不要把“顺序调用四次”写成“并发队列已通过”。同样，本轮不主动恢复 27B 与 Fish 同时推理来做共存压力测试。

因此即便本轮通过，也只能提出“独立串行、短分段章节配音已达到本轮门槛”的结论，**不能直接宣称整本小说、多人队列或内容工厂并行生产 verified**。按照项目完整验收要求，缺失项保持未完成；本轮执行者不得改推荐栈或降低验收范围后自行晋级。

## 12. 报告、日志与最终回复契约

结果摘要 `summary.json` 至少包含：run ID、状态/停止原因、版本/参数/参考哈希、预期/完成/首次失败/修复数量、逐项 verdict、总时长/RTF/p50/p95、资源基线及峰值增量、异常索引、人工复核是否完成、所有证据路径。

正式报告从自己的新 `artifact.json` 生成自包含 HTML，可以复用项目 `scripts/render-evaluation-record.py`。**不要直接调用 `build-fish-s2-report.py` 并把旧的 13 段结果当作本轮结果**，那个脚本固定读取首轮目录。报告须把实测、推断、未测和待用户听评分开，标注每个数值的来源与计量口径。

交付清单：

1. 新执行器/监控器/分析器及其干运行结果、启动和恢复命令。
2. 冻结的用例 manifest、文本与参考哈希；独立运行预检证据。
3. 全部原始日志、资源时间序列、音频索引、异常和重试记录。
4. `summary.json`、正式 `artifact.json`、自包含 `report.html`、来源说明。
5. 匿名试听包、评分 CSV、整章拼接及时间轴（留外部实验目录）。
6. 追加 `docs/DECISIONS.md`，写本次结论或待听评状态；新交接文档并更新 README 指针。保留旧报告、已有未提交修改，不自行提交/推送。

声明完成前核对文件存在、非零、JSON 可解析、哈希绑定、expected task IDs 与实际任务集合一致；资源止损/超时退出要有非零退出码和明确结果。HTML 如未完成视觉检查，应明示原因，不伪写已通过。

给用户最后只需说明：执行阶段、测试通过/失败/未测项、速度与内存关键值、待试听清单和报告路径。没有读取到证据就写未知，不凭第一轮结果补齐。
